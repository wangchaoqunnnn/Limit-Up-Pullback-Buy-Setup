# 涨停回调低吸战法 · 量化选股与分析平台

> 把一套经验型的 A 股短线战法，翻译成**可执行、可复现、可验证、可视化**的量化选股系统。

| 项目 | 说明 |
|---|---|
| 后端 | Python 3.12 + FastAPI（异步） |
| 前端 | React 18 + TypeScript + Vite，图表全部手写 SVG |
| 行情数据 | **真实行情 · 三源自动故障切换**（东方财富 / 腾讯财经 / 新浪财经） |
| 刷新策略 | **开盘期间每 30 秒自动刷新**，收盘后自动停止 |
| 缓存 | SQLite 日线增量缓存（首轮全量后只补增量） |
| 部署 | Docker 多阶段构建，单容器同源部署，一键脚本 |
| 测试 | 后端 `pytest` 95 项全部通过；前端零类型错误 |
| 视觉质量 | 独立视觉评审：首页 93、信号选股 87、个股详情 84（满分 100） |

## 行情数据：真实数据 + 多源故障转移

网站默认使用**真实 A 股行情**，并内置三层保障，避免单一数据源故障导致服务不可用：

```
第一层  多真实源   东方财富 / 腾讯财经 / 新浪财经（优先级可配置）
第二层  故障转移   取列表、取日线、取实时行情各自独立切换；
                  失败/空结果/数据量不足均触发切换；
                  失败源进入指数退避冷却，冷却后自动恢复
第三层  合成兜底   仅当全部真实源不可用时启用，界面显著标注「演示数据」
```

### 覆盖全部 A 股（不遗漏任何板块）

默认 `UNIVERSE_SIZE=0` 表示**不限量、覆盖全部 A 股**。实测全市场规模：

| 板块 | 代码段 | 数量 | 涨停幅度 |
|---|---|---|---|
| 主板 | 沪 `600/601/603/605`、深 `000/001/002/003` | 3,195 | 10% |
| 创业板 | `300/301/302` | 1,407 | 20% |
| **科创板** | `688/689` | **616** | 20% |
| **北交所** | `920` 及存量 `43x/83x/87x/88x` | **343** | 30% |
| **合计** | | **5,561** | |

两个容易被漏掉的板块，本项目已专门处理：

- **科创板**：腾讯排行榜不含它（只有 `GP-A` 与 `GP-A-CYB`），必须用新浪 `sh_a` 节点补齐；
- **北交所**：只在新浪 `hs_a` 节点里（`920xxx`），且**腾讯日线对北交所只返回 1 根 K 线**——
  系统通过「数据量不足也算取数失败」自动切换到新浪，拿到完整历史。

> `920` 段必须识别为**北交所**而非深交所：否则涨跌停幅度会按 10% 计算（实际 30%），
> 直接影响涨停判定。这一点已用腾讯 `stock_type` 标记实测确认。

### 关键点：某个源挂了不会整体降级

实测日志（本机网络阻断东方财富）：

```
eastmoney  失败 → 自动切换
tencent    股票列表缺科创板/北交所（4602 只）→ 继续尝试下一个源
sina       股票列表覆盖完整（5561 只，四板块齐全）→ 采用
日线：tencent 对北交所只给 1 根 → 判定取数失败 → 切 ths（同花顺）拿到完整历史
```

即系统**按操作逐个源尝试并校验数据质量**，既能故障转移，也能识别「不报错但数据不全」的隐蔽情况。

### 性能实测（全市场 5,561 只）

| 场景 | 实测 | 说明 |
|---|---|---|
| `/api/v1/signals`（选股核心接口） | **0.2 s** | 走扫描结果缓存，与股票池规模无关 |
| `/api/v1/stocks` | 0.14 s | 走日线缓存 |
| `/api/v1/market/clock` | 0.03 s | 纯计算 |
| `/api/v1/market/overview` | 18～39 s | 需全市场日线 + 情绪聚合；已按扫描批次缓存聚合结果 |
| `/api/v1/backtest` | 24 s | 全市场历史回放，已加候选预筛（优化前 31 s 起） |
| `/api/v1/settings` | 3.7 s | 深度模式才拉股票池 |
| **部署后首轮全量拉取** | **约 8 分钟** | 5,561 只 × 250 根日线，一次性；之后走增量缓存 |

> **关于「开盘期间每 30 秒刷新」**：刷新间隔、缓存 TTL、前端轮询节奏都已按 30 秒实现并生效
> （`/api/v1/market/clock` 下发 `shouldPoll` 与 `intervalSeconds`）。
> 但**全市场规模的取数与聚合本身需要数十秒**，因此 30 秒是「数据新鲜度目标」，
> 而不是「每 30 秒一定能完成一轮全市场重算」。追求更快的刷新可以：
> 调小 `UNIVERSE_SIZE`（例如 1000，按板块轮转截取，四个板块都保留代表）、
> 或调高 `KLINE_CONCURRENCY`（注意新浪反爬上限约 24）。
> 选股核心接口 `/signals` 始终是亚秒级响应，交互不会卡顿。

### 已知限制

- **部分北交所新股历史不足**：实测约 18 只（如 `920059`/`920071`）在腾讯与新浪都拿不到
  足够历史（< 20 根），系统会记录负缓存并在 20 分钟内不再重试，不会反复拖慢刷新。
  这些标的在补足数据后会自动重新纳入。
- **新浪列表接口有反爬限流**（HTTP 456，封禁约 10 分钟）。全市场列表一天只抓一次并落盘快照，
  正常使用不会触发；若在排查阶段频繁重启，可能遇到限流，等待即可恢复。

### 数据源模式

| 模式 | 行为 | 用途 |
|---|---|---|
| `auto`（默认） | 按优先级尝试真实源，全部失败才降级演示数据 | 一般部署 |
| `real` | 同上但**绝不降级**，全失败即报错 | 生产环境（及早暴露源故障） |
| `eastmoney` / `tencent` / `ths` / `sina` | 强制单源 | 排查字段差异 |
| `synthetic` | 强制内置演示数据，完全离线 | 演示 / 内网 / 测试 |

### 刷新策略（开盘期间每 30 秒）

| 时段 | 是否自动刷新 | 缓存 TTL |
|---|---|---|
| 09:30–11:30 / 13:00–15:00 连续竞价 | ✅ 每 30 秒 | 30 秒 |
| 09:15–09:30 集合竞价 | ✅ 每 60 秒 | 60 秒 |
| 11:30–13:00 午间休市 | ✅ 每 60 秒 | 60 秒 |
| 盘前 / 15:00 后 / 周末与法定休市 | ❌ 停止轮询 | 300 秒 |

前端通过 `/api/v1/market/clock` 获取市场时钟，据此决定是否轮询；收盘后自动停止，
并在顶栏显示「已收盘 · 下次开盘 MM-DD HH:mm」。切换浏览器标签页时暂停，回到前台立即刷新。

### 数据源可观测

- 顶栏实时显示当前生效数据源（东方财富 / 腾讯财经 / 新浪财经 / 演示数据）与市场状态；
- `/api/v1/sources` 提供各源健康度、板块覆盖分布，以及「每个操作最近实际使用的源」；
- 设置页有独立面板展示以上信息，并支持手动「重新探测」（会重置健康度，让被跳过的源重新参与）。

## 这个项目解决什么问题

原素材作者的观点很反直觉，但也很清晰：

> **「涨停是主力的出货舞台，回调才是散户的低吸机会。」**
> 追高是接盘博弈，回调是顺势低吸。

他把散户亏损归因于「盲目追高、频繁打板、乱做连板妖股」，转而只做一件事：**优质首板之后的缩量回调企稳低吸**，赚第二波拉升的确定性利润。

问题在于，这套方法散落在九张图文里，全是「放量实体」「持续缩量」「守住支撑」这类**定性描述**——人脑每天翻几百只票根本执行不了，还会因为情绪走样。

本项目把它工程化：

| 原文的定性说法 | 系统中的定量判据 |
|---|---|
| 只做低位首板，不做连板妖股 | 前 1~2 日无涨停 **且** 120 日位置比例 ≤ 0.80 |
| 只做放量实体涨停，拒绝缩量一字板 | 量比 ≥ 1.2 **且** 换手率 3%~25% **且** 排除一字板 |
| 缩量回调是洗盘，放量回调是出货 | 回调每日量 < 涨停日量 **且** 逐日递减；否则一票否决 |
| 守住关键支撑 | 涨停实体半分位 + 涨停日开盘价（主力成本底线） |
| 小阳十字星收尾，拒绝大阴线 | 末端实体幅度 ≤ 1.5% 且重心不下移；单日 ≤ −3% 视为破位 |
| 板块情绪同步回暖 | 同行业成分股 5 日涨幅 + 涨停占比 + 上涨家数 → 情绪分 |
| 五个信号必须共振，缺一不买 | 五信号全部 `passed` 才输出「可低吸」结论 |

## 核心功能

- **市场总览** —— 指数走势、市场情绪仪表盘（冰点/偏冷/中性/偏暖/过热）、涨停与炸板家数、五信号通过率、板块热度榜
- **信号选股（核心）** —— 一键全市场扫描，按评分排序输出可低吸/观察标的，五大信号明细可展开
- **个股深度分析** —— 手写 SVG 专业 K 线图（成交量副图、均线、涨停标记、支撑位虚线、买入区间色带、十字光标、缩放平移）、评分环、支撑位阶梯、交易计划卡、风险卡
- **回测分析** —— 信号历史回放，统计胜率、盈亏比、最大回撤、净值曲线、收益分布、分信号表现
- **自选低吸池** —— 持仓状态跟踪（观察中/已触发/已止盈/已止损），跌破止损自动标记
- **战法规则与参数** —— 原文四条纪律与避坑要点完整呈现，五大信号权重与所有阈值可在界面调节
- **优雅降级** —— 真实行情接口不可用时自动切换到内置演示数据，产品功能完整可用，界面明确标注

## 快速开始

### 方式一：一键部署（推荐，云服务器）

```bash
# Linux / macOS
git clone <仓库地址> && cd Limit-Up-Pullback-Buy-Setup
chmod +x deploy.sh
./deploy.sh
```

```powershell
# Windows（需先启动 Docker Desktop）
pwsh -File .\deploy.ps1
```

脚本会自动：检查环境 → 生成 `.env` → 校验配置 → 放行防火墙 → 构建镜像 → 启动容器 → 健康检查 → 打印访问地址。

部署完成后浏览器访问 `http://<服务器IP>:8000`（记得在云控制台安全组放行对应端口）。

### 方式二：Docker Compose 手动部署

```bash
cp .env.example .env       # 按需修改端口与数据源模式
docker compose up -d --build
docker compose logs -f --tail=200
```

### 方式三：本地开发

```bash
# 后端（终端 1）
cd backend
py -m venv .venv                               # Linux/macOS: python3 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m uvicorn app.main:app --reload --port 8000

# 前端（终端 2）
cd frontend
npm install
npm run dev                                    # http://127.0.0.1:5173
```

后端接口文档：`http://127.0.0.1:8000/docs`

## 配置说明

所有配置通过环境变量注入，模板见 `.env.example`。常用项：

| 变量 | 默认 | 说明 |
|---|---|---|
| `HOST_PORT` | `8000` | 宿主机对外端口（云安全组需放行） |
| `DATA_SOURCE_MODE` | `auto` | `auto` 自动切换 / `real` 只用真实数据不降级 / 单源 / `synthetic` 完全离线 |
| `DATA_SOURCE_ORDER` | `eastmoney,tencent,ths,sina` | 真实数据源优先级（故障转移顺序） |
| `REFRESH_INTERVAL_SECONDS` | `30` | **开盘期间刷新间隔**（后端 TTL 与前端轮询共用） |
| `CACHE_TTL_SECONDS` | `300` | 非开盘时段的缓存有效期 |
| `UNIVERSE_SIZE` | `0` | **0=覆盖全部 A 股**（约 5561 只）；设正整数则按板块轮转截取 |
| `KLINE_CONCURRENCY` | `24` | 日线抓取并发（过高会被新浪限流） |
| `LOG_LEVEL` | `INFO` | 日志级别 |
| `TZ` | `Asia/Shanghai` | 时区（影响交易时段判定） |

> **代码中无任何绝对路径与硬编码地址**：后端路径均由 `Path(__file__)` 推导，前端请求一律走相对路径 `/api/v1`。
